> 本文断言"`market_visible` 没有策略 ⇒ 再多数据也无法买入，覆盖不存在"。**这个断言是错的。**

> 它对**任意计算族**都成立。所以"没有 `market_visible` 策略"并不构成不可逾越的阻断。

> 第 92 轮用引擎自己的字段重新测了最新 3,000 条被拒记录：

## 0. 结论（一句话）

**`market_visible` 是引擎可计算的入场族之一，而当前激活定义里没有任何策略声明这个族。**
于是这些代币的 `family_arms` 为空，唯一可达的拒绝原因就是
`no_active_matching_entry_policy`（`store.py:29958-29964`）——
**再多的数据、再高的流动性、再长的观察都无法让它们被买入，因为覆盖不存在。**

系统级规模：**154,327 行 / 27,006 个代币 = 全部入场评估的 34.8%**。

## 2. 根因：族覆盖缺口（引擎自己记录的证据）

激活定义 `funding-20260906-v002-final-1000`：**127 个策略，0 个暂停**。

| | 族 |
|---|---|
| **可计算**（`store.py:29845-29850` 的 `required_cooldown` 只有这四个键） | `broad_launch`、`flow_burst`、`reawakening`、**`market_visible`** |
| **已部署**（定义里的 `entry_family`） | `flow_burst`(64)、`broad_launch`(35)、`shadow_momentum`(14)、`dex_visible_successor`(14) |
| **可计算但未部署** | **`market_visible`、`reawakening`** |

**最新 4,000 条被拒评估的族分布**（有界抽样，非全量）：

| 族 | 行数 | 占比 |
|---|---|---|
| **`market_visible`** | **3,725** | **93.1%** ← 无策略 |
| `flow_burst` | 171 | 4.3% |
| `broad_launch` | 103 | 2.6% |
| `reawakening` | 1 | 0.0% ← 无策略 |

**38 个病例的全部 1,071 条评估**：`market_visible` **230**（无策略）、
`broad_launch` 48、`flow_burst` 7，其余为观测车道的 `cohort_experiments`/`pattern_experiments` 记录。

**为什么这是逻辑断点而不是合理拒绝**：`family_arms` 的过滤条件是
`entry_family in {computed_family, "market_visible"}`
（`store.py:29915-29926`）——**`market_visible` 被当作通配族与任意计算族并列**，
这说明设计上就是允许存在 `entry_family="market_visible"` 的策略的。
**部署里没有，是遗漏，不是有意拒绝。**

## 3. 一个诊断标签缺陷（同源）

`no_active_matching_entry_policy` 这个名字读起来像"策略被暂停了"，实际含义是
**"这个代币算出来的族没有任何策略"**。激活定义 **0 个暂停策略**，
所以任何按字面理解这个名字的排查都会走错方向——我此前几轮就把它列成"未解释项"。

## 4. 一个数据库性能缺陷（本轮附带发现）

`chain_meme_trader_v6_entry_evaluations` 有 **442,920 行**，而它**全部 5 个索引都以
`definition_version` 开头**。因此任何只按 `token_id` 过滤的查询**用不上任何索引**：

| 查询 | 耗时 |
|---|---|
| `COUNT(*) WHERE token_id=?`（无版本前缀） | **222.69 s** |
| 同一张表，带 `definition_version` 前缀 | 索引命中 |

我的第一版病例查询就是因此超时 600 s 的。已把工具改成**一律带版本前缀 + 批量分组**。
另外 `tokens` 表没有 `address` 索引，逐地址查询会全表扫描（64,518 行 / 22.8 s），
工具改为**一次扫描进内存**。

## 5. 修复方向（**本轮不部署**，按用户约束落地）

用户约束：新策略必须以**额外独立策略模块**加入，严禁修改/替换现有策略。
因此正确动作是**新增声明 `entry_family = "market_visible"`（以及 `reawakening`）的策略**，
而不是改那 127 个既有策略中的任何一个。

| 优先级 | 动作 | 依据 |
|---|---|---|
| **P0** | 新增 `market_visible` 族的入场策略模块（含其自己的过滤、仓位、退出） | 34.8% 的评估、38 例中的 8 例被此单点阻断；`market_visible` 在设计上是通配族 |
| **P0** | 新增 `reawakening` 族的入场策略模块 | 同为可计算未部署族 |
| P1 | 把 `no_active_matching_entry_policy` 拆成"族无策略"与"策略被暂停"两个原因 | 现名误导排查方向 |
| P1 | 给 `chain_meme_trader_v6_entry_evaluations` 加 `(token_id, id)` 索引，或统一查询带版本前缀 | 222 s 全表扫描 |
| P1 | 查清 5 个未入库的 EVM 地址属于哪条链、为何未发现 | 发现覆盖缺口 |

**必须同时说清的边界**：打开族覆盖会显著增加开仓数量，但第 85 轮的结论不变——
**94 个代币里 6 个盈利**，所以"更多开仓"本身不是盈利能力；
`market_visible` 包含大量**零成交、池龄数百天**的池子（抽样行：`m5_trades=0`、`age≈303 天`），
新模块必须带自己的活跃度过滤，而不是把这类池全部放进来。

## 7. 新增常设规则（接 §10.6，编号 58–60）

58. **一个"原因"标签的措辞会决定排查方向；先去代码里读它何时被赋值。**
    `no_active_matching_entry_policy` 听起来是"策略被暂停"，实际只在
    `family_arms` 为空（族无策略）时赋值，而当时 0 个策略被暂停。我此前几轮把它当"未解释项"。
59. **把"可计算的取值集合"与"已部署的取值集合"并列打印。**
    可计算族 4 个、已部署族 4 个，**交集只有 2 个**——单这一点就能解释 34.8% 的拒绝。
    **枚举两个集合的交集，比逐个案例追查快得多。**
60. **索引前缀决定查询形态；不带前缀的过滤会退化成全表扫描。**
    442,920 行的表、5 个索引全以 `definition_version` 开头 ⇒ 只按 `token_id` 过滤要 **222 s**。
    **写诊断查询前先读 `pragma index_list`；工具里要把这个约束写成断言。**
