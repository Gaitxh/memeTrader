## 0. 一句话结论

1. 第 72 轮测出主导闸门是 `await_distinct_dex_trajectory_frame`（46.41% 的逐臂判定、
   98.9% 触及它的配对最终停在它上面）。**本轮把它追到了判定它的那一行代码**
   （`store.py:27781-27785`），从此它不再是一个"原因字符串"，而是一个**可计算的条件**。
2. **通过条件是完全确定的**（`dex_trajectory.window()`，第 49-55 行）：要让这个闸门放行，
   一个 (token, pair) 序列必须在某个时刻同时满足
   **① 至少有 3 帧 ② 跨度 ≤ 30 秒 + 余量 ③ 相邻帧间隔都不超过 30 秒**。
3. **实测这条链在数据上几乎不可能满足**：
   - 只有 **13.6%** 的 token 序列曾经拿到 ≥3 帧；
   - **63.7% 只有 1 帧，86.4% 只有 ≤2 帧**；
   - 逐帧检验：只有 **28.98%** 的帧在那一刻**能够**形成 30 秒窗口；
     能形成窗口的序列只占 **1.25%**（215 / 17,250）。
4. **否证假设一（节流不足）**：如果问题在轮询速度，那么把节流从 15 秒压到 5 秒应该大幅改善。
   实测**几乎不动**——在观测到的生存期内按固定节流重放，满足窗口的序列数
   **5 秒节流 5,991 / 10 秒 5,967 / 15 秒 5,937 / 20 秒 5,918（总 6,258）**。
   **改节流最多买到 0.9%。**
5. **否证假设二（帧被丢弃）**：我怀疑 30 秒入库上限在丢帧。实测
   `observed_at → recorded_at` 延迟 **p50 0.868 秒、p99 24.9 秒，超过 30 秒的只有 7 帧（0.008%）**。
   **没有东西被丢弃。**
6. **真正的约束是"帧供给"**：**86.4% 的 token 无论轮询多快都永远拿不到 3 帧**，
   因为系统**总共只取到 1–2 帧**。这不是节流问题，是**观测覆盖/租约驻留**问题。

## 1. 判定行本身（第 72 轮只看到原因字符串，本轮看到条件）

```python
# store.py:27781-27785
if p.get('requires_distinct_trajectory_frame'):
    trajectory = self._trajectory_engine_for(p)
    observed   = trajectory.pools.get((token.token_id, pair_address), {}).get('features', {})
    if (observed.get('observed_at') != iso(snapshot.observed_at)
            or not observed.get('windows', {}).get('30')):
        entry_blocked[p['arm_id']] = 'await_distinct_dex_trajectory_frame'
```

**两个独立条件都能触发这个原因字符串**（字符串不区分它们）：
- **(a)** 轨迹里那一帧的 `observed_at` 与当前快照的 `iso()` **字符串不相等**；
- **(b)** 轨迹特征里**没有 `windows['30']`**。

### 1.1 我先怀疑 (a) 是一个字符串格式化缺陷——**已否证**

`observed_at` 的两侧分别是"SQLite 里存出来的字符串"和
`iso(datetime)`（`models.py:45-46`，恒定输出 6 位微秒 + `Z`）。
如果任何生产者在写时间戳时省略微秒，两侧就会**指向同一时刻却比较不等**，
于是每一帧都会被报成"等待不同的轨迹帧"。**这是一个足以吞掉舰队近一半判定的缺陷，所以必须实测。**

**实测否证**：

| 列 | 格式 | `iso(parse_time(v)) == v` |
|---|---|---|
| `token_snapshots.observed_at` | 100% 微秒6位+Z | **20,000 / 20,000 = 100.00%** |
| `token_snapshots.ingested_at` | 100% 微秒6位+Z | **20,000 / 20,000 = 100.00%** |
| `token_snapshots.recorded_at` | 100% 微秒6位+Z | **20,000 / 20,000 = 100.00%** |
| `chain_meme_trader_market_mark_history.observed_at` | 100% 微秒6位+Z | **20,000 / 20,000 = 100.00%** |

**所以 (a) 的不相等是真实的不相等——那一帧确实不是当前帧。闸门是有意义的，不是格式事故。**

## 2. 通过条件的实测（`dex_trajectory.window`，逐行对应）

```python
def window(rows, seconds):                                          # line 49
    end = rows[-1]['t']; eligible = [i for i,r in enumerate(rows) if r['t'] <= end-seconds]
    if not eligible: return None                                    # ① 需要满额回看窗口
    part = rows[eligible[-1]:]
    if end-part[0]['t'] > seconds+max(5,seconds/3): return None     # ② 跨度 ≤ 30+10 秒
    if any(b['t']-a['t']>30 for a,b in zip(part,part[1:])): return None  # ③ 相邻间隔 ≤ 30 秒
    if len(part)<3: return None                                     # ④ 至少 3 帧
```

**在每一个序列的每一帧上套用这三条（n = 66,145 帧）：**

| 结果 | 帧数 | 占比 |
|---|---|---|
| **能够形成 30 秒窗口** | **19,170** | **28.98%** |
| 跨度超过 30 秒 + 余量 | 25,116 | 38.0% |
| 没有满额回看（该帧时序列还不到 30 秒） | 18,049 | 27.3% |
| 相邻间隔超过 30 秒 | 3,810 | 5.8% |

**能形成窗口的序列：215 / 17,250 = 1.25%。**

**帧数分布（问题最清楚的一张表）：**

| 帧数 | 序列数 | 占比 |
|---|---|---|
| **1** | **11,000** | **63.7%** |
| **2** | 3,913 | 22.7% |
| 3–4 | 969 | 5.6% |
| 5–9 | 762 | 4.4% |
| 10–29 | 418 | 2.4% |
| 30+ | 196 | 1.1% |

**p50 = 1 帧。只有 13.6% 的序列达到窗口要求的最低 3 帧。**

## 3. 否证"节流不够"（这一条决定了要不要动频率参数）

**反事实重放**：保留每个序列**实际观测到的生存期**，在其中按固定节流生成帧，再套用窗口的三条规则：

| 节流 | 满足窗口的序列数（总 6,258） |
|---|---|
| 5 秒 | 5,991 |
| 10 秒 | 5,967 |
| 15 秒 | 5,937 |
| 20 秒 | 5,918 |
| 30 秒 | 0 |
| 60 秒 | 0 |

**从 15 秒压到 5 秒只多 54 个序列（+0.9%）。** 而 30/60 秒节流下**一个都不满足**——
因为窗口要求"相邻间隔 ≤ 30 秒"，正好卡在 30 秒的节流上会因抖动必然违规。

**这否证了"提高扫描频率就能改善"这一方向**：
在**帧总数**受限的前提下，节流只影响帧在时间上的排布，不影响帧的数量。
（附录：实测相邻帧间隔 p50 **17.10 秒**、p75 76.93 秒、p90 334.05 秒；
60.0% 的间隔 ≤30 秒、42.4% ≤15 秒。间隔的中位数**本来是够的**，
不够的是**帧数**。）

## 5. 系统是"看一次就不再看了"（引擎自己的复核次数）

用引擎自己记录的评估行数交叉验证（**每一行 = 一次评估**）：

| token 类别 | 数量 | 评估行数 |
|---|---|---|
| 只有 1 帧的 token | 11,266 | **82.1% 恰好 1 行**，17.9% 有 2–5 行，0 行 >5 |
| ≥3 帧的 token | 2,409 | p50 **8** 行、p75 16 行、max 2,209 |

- **每个有快照的 token 都有评估行**（17,673 / 17,673），所以覆盖不漏。
- **只有 1 帧的 token，82.1% 只被评估一次**；那 17.9% 被评估 2–5 次的，
  **观测时间中位数只有 7.9 秒**（p90 18.0 秒）。
- 全 epoch：**88,275 次评估 / 68,502 帧 = 每次评估对应 1.29 帧。**

**∴ 系统的实际行为是：看到一个 token 一次、评估一次、然后不再看它。**
单帧 token 因此**在结构上必然**被 `await_distinct_dex_trajectory_frame` 拦下——
窗口要求 3 帧，它只有 1 帧。**但这不是闸门"过严"，而是它根本没有原料。**

## 7. 可落地的方向（按投入产出比）

### P0：把"帧数不足"变成一级可观测指标（纯读取）

现在要回答"这个 token 为什么没开仓"必须手工重建帧序列。建议在
`scripts/outcomes_readout.py` 之外再加一个只读视图，直接给出
**每个 token 的帧数、是否曾满足窗口、以及卡在哪一条**（三条规则的哪一条）。
**零行为变更**，但把本轮的分析从"十几个临时脚本"变成"一条命令"。

### P1：租约驻留（**用户决策项，本 session 不触碰**）

真约束是"能让多少 token 持续被观测"。第 65 轮已证明**延长租约**与**提高节流**都不是杠杆
（产出率与吞吐量互相抵消；本轮又独立否证了节流），**只有槽位数量是**。
边际产出 ≈ 4.7 个密集窗口/槽位/小时。

### P1：单帧 token 的处置（**有效性**）

63.7% 的 token 只被观测一次。它们**在结构上不可能**通过轨迹闸门，
却仍然占用了：一次发现、一次入库、一次评估、以及 23 个臂各一次判定（全 epoch 5.96M 判定的大头）。
**如果能用一次观测就判定"这个 token 不值得继续观测"，就能把这部分算力释放出来**——
这是"减少无效计算与空转"（用户明确列出的目标）最直接的着力点。
**注意**：这需要先证明"单帧可判"是可行的，本轮**没有**证明，只提出了方向。
