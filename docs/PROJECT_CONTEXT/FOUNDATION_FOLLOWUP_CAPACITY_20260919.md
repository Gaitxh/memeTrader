# 基础链优化：信号产生时提前保护后续确认帧容量（2026-09-19）

## 观察到的断点

08:34 UTC 的生产遥测显示，持仓行情仍保持最高优先级且当时无覆盖缺口，但普通后台 DEX 工作会在策略信号产生后、后续确认采集真正开始前占满低优先级容量：

- `dex_phase_followup.slot_ms_p95 = 14640 ms`（31 个样本，6 次失败）；
- 被动计算队列等待 `p95 = 16.191 s`（461 批已处理，0 丢弃）；
- 同期策略信号只有 60 秒原始有效期，因而“采集排队 + 判断队列”会消耗一半左右的因果窗口；
- 持仓链路保留独立高优先级，不能用增加总并发来换速度。

根因是容量保护只在较慢的 pattern observer 已经选中后续请求时才发布。信号从被动批次产生到 observer 下一次运行之间，普通发现、补全和研究请求仍可拿走第五个低优先级槽位；已有保护无法抢占已在运行的请求。

## 实施

新增 `followup_capacity.py` 并在 cohort 信号写入 `_cohort_pending` 的同一时刻发布容量保护：

- 只读取每个信号原有的 `recorded_at`；
- 只保护 `60 - age` 的剩余原始有效期，不续期、不回填、不接纳未来时钟；
- 只让已有容量门控暂缓第五个普通后台请求；不新增 HTTP 请求、不提高总并发；
- 后续确认仍使用原有同池、鲜度、安全、下一帧和 Paper 成本规则；
- 持仓/待退出的三个保留槽位不变，发现与补全只被短暂延后并沿用现有重试。

这同时改善 `数据采集 → 本地计算 → 策略判断` 的时序：重要信号更早向调度器表达优先级，减少确认帧在后台工作之后排队的机会。它不改变发现来源、覆盖集合或策略阈值。
