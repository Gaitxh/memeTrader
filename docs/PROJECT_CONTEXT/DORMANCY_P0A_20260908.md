## 原因与边界

`chain_meme_market_marks_once` 在整个持仓刷新开始时清除全局 idle 事件，直到所有网络请求、落库和退出判断结束才恢复。候选取数、资料补全、被动分析和低优先 DEX 槽位都等待这个事件。因此即使已有总计 8 个请求槽位、低优先最多 5 个的限制，持仓请求等待网络时后台仍不能使用空余容量。

这证实一种持续运行饥饿来源，不能仅凭它认定所有策略沉寂、全部亏损或重启激活都已解释。

## 补充修复：HTTP 请求启动优先级

响应 `C2C-20260908-DORMANCY-P0A-PRIORITY-START-ADDENDUM-05`。上一版保留了持仓的并发容量，但 HTTP 层按 host 的启动限速仍使用 FIFO Lock，并在锁内等待间隔；新到达持仓请求可能排在已有后台请求之后。独立复核确认这一边界。[Python 官方文档](https://docs.python.org/3/library/asyncio-sync.html#asyncio.Lock)说明 Lock 的等待顺序；不能把信号量容量预留等同于启动顺序优先。

本次仅对 `api.dexscreener.com` 的启动仲裁使用 Condition 与高/低两个等待队列，同级保持先到先启动。等待间隔时释放 Condition，持仓新需求能够唤醒并抢占尚未开始的后台请求。每次实际获准启动前重新检查原有 host 间隔和共享退避时间；取消时移除自己的等待项并唤醒其他任务。启动获准就释放轮次，HTTP 响应不占有仲裁锁，不中断已经在途的后台请求。

Runtime 原有 `high_priority` 标志通过请求作用域 ContextVar 传至 HTTP 层，退出作用域时恢复；`fresh=True` 的后台行情仍为低优先。Dex 的 429 重试也走同一启动仲裁，避免重试重新制造锁内阻塞；其他 provider 维持原有行为。默认 0.25 秒启动间隔、8/5 请求容量、3 个持仓预留和所有策略/资金设置不变。

本次 10 个定向用例通过：实际 Runtime→Dex→Http 两个后台先排队但两个持仓先启动、后台在持仓响应前恢复；高/低取消各一个；后台429重试让位；原429跨端点退避两个；Gecko与普通其他host间隔；fresh无内联429重试；8/5容量与取消两个。独立 Agent 审阅了 Condition、ContextVar及重试/取消路径，未发现具体阻碍。未重复运行无关全套测试。
