## 1. 纠错 A：滑点常数被当成了行情

### 我做错了什么

第 69b 轮为量化下行信息率，算了每个仓位的 running low：

```python
ratio = MIN(mark.price_usd) / position.entry_signal_price_usd
econ  = 0.96 * ratio - 1
```

得到"58.03% 触及 −10%、44.85% 触及 −35%"这类结果，看起来下行侧信息率远高于上行侧。

### 怎么发现的

做标定：拿部署中的 `hard_stop_return = −0.35` 与实际退出原因对照——
mark 序列说 44.85% 该触及，实际只有 **29.41%** 走 `market_mark_hard_stop`，差 **1.53 倍**。
查第一帧：

```
p5   first-mark econ =  -0.0440
p25  first-mark econ =  -0.0400
p50  first-mark econ =  -0.0400
p75  first-mark econ =  -0.0400
p95  first-mark econ =  +0.0021
```

**中位数仓位的第一个 mark 就是 −4.00%**，而且 p25 = p50 = p75 **全等于 −0.0400**——一个常数。
那就是 4% 买入滑点。`ex/en` 的 p1 到 p99 **全部等于 1.0400**。

**这是同类错误的第三次**（第 52 轮经济核、第 41 轮锚点）。共同点：**在一个含常数的量上直接算比率**。

## 2. 纠错 B：我测的不是引擎用的那个量（本轮最重要的一条）

### 69f 轮的对照

| 对照结果 | 笔数 |
|---|---|
| 引擎列与 history MAX **完全一致** | 2,255 |
| **history MAX 高于引擎列** | **1,471** |
| history MAX 低于引擎列 | 163 |
| 无可用 history | 3 |

最坏情形 `×5.406`：引擎记 3.544e-05，history 记 1.0001916e-04。

**机制**：`history` 的连接是 `token_id` + `recorded_at >= opened_at`，
**没有限定入场池、也没有收盘上界**。于是一个**陈旧的第二池**或**平仓之后的行情**
都能伪造出任意倍数。这正是**规则 10**（窗口类统计必须先按池身份过滤，再取极值）
和第 68 轮记录里的同类——我写下过这条规则，却又犯了一次。

### 加上池与窗口约束后的对照

```
exact agreement : 3529
history higher  :   53
history lower   :  302   （引擎列可以高于采样到的 history，符合预期）
not comparable  :    8
```

**1,471 → 53。** 所以错的是我的连接，不是数据。

### 引擎的权威基准（我直接读了源码）

```
store.py:35686-35705
    entry_price     = position.entry_execution_price_usd OR entry_signal_price_usd
    high            = max(position.highest_signal_price_usd, mark_price)
    economic_return = current_economic_value / stake - 1

paper_execution.py:118
    net = quantity * price * (1 - sell_slippage_bps/1e4)      -> 0.96
```

**∴ `econ = 0.96 * (high / entry_price) − 1`，而 `entry_price` 优先取 `entry_execution_price_usd`。**

### 独立验证核

用引擎自己的 `highest_economic_value_usd`（存量口径）反推：

```
positions where stake-relative HEV matches 0.96*(high/entry)-1 within 2e-3: 3708/3892
```

**3,708/3,892 = 95.3% 吻合**，核得到确认。

## 5. 下行侧：仍然是 history bound，且**不可用引擎交叉验证**

引擎**只记录 `highest_signal_price_usd`（上行的 running high），没有任何下行的 running low 列**。
所以：

- 下行侧**只能**从 mark history 求，**没有引擎侧的量来对照**——本轮建立的"两口径互相印证"
  这个保护措施对下行侧**不存在**。
- 因此第 69d 轮的下行数字（`−10%` 63.70%、`−20%` 51.67%、`−35%` 45.24%）**标记为
  history bound、未经引擎验证**，引用时必须带上这个限定。
- 一个**可用的旁证**是退出路径标定：1,070 笔实际走 `market_mark_hard_stop` 的仓位里，
  **918 笔（85.8%）** 的 mark 序列确实显示低点触及 −0.35。这说明序列**方向正确**，
  但**不能**排除系统性偏低。

## 6. 硬止损阶梯：否决（理由与数字）

| 配对 | P（history bound） | 需要 cohort |
|---|---|---|
| `−10%` vs `−60%` | 0.2933 | **68** |
| `−10%` vs `−50%` | 0.2531 | 79 |
| `−10%` vs `−40%` | 0.2037 | 98 |
| `−20%` vs `−60%` | 0.1730 | 116 |

**否决理由（写清楚，免得以后重开）：**

1. **68 vs 100 个 cohort**——下行侧确实更宽，但**下行分布是饱和的**：越过 −5% 之后曲线陡降再变平，
   从 −20% 到 −60% 只多覆盖 13 个百分点（51.67% → 38.39%），因为**一半以上的仓位一路跌到底**。
   **失败的仓位彼此无法区分。** 上行则在 +10% 到 +25% 之间还有 20 个百分点可以分开。
2. **槽位才是真约束，不是统计功率。** 载体臂每臂 cap = 8（用户授权、全舰队统一），
   四臂合计 32 槽，实测吞吐 24.3 cohort/h。68 和 100 **都在 3–4 小时量级**。
   **在槽位受限的系统里，把统计效率提高 30% 没有意义。**
3. **一个更该建但本轮不建的候选**：**时间止损阶梯**。时间轴信息率极高且与止损宽度正交
   （超过 1 分钟还有 85.68% 未平、5 分钟 64.13%、15 分钟 28.24%、30 分钟 15.53%、60 分钟 5.69%）。
   **本轮不建**，因为已有三个 P0 读数在槽位队列里排队，再加只会拉长每个读数的等待。
