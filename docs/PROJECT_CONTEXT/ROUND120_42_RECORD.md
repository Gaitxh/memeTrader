# ROUND 120-42 — 入场时"流动性下限"这条线索：实测为零，关闭

## 1. 线索本身（它为什么看起来有希望）

全部 818 个写下线仓位的关闭原因都是同一个字符串：

```
dex_pool_liquidity_below_configured_floor_writeoff
```

即"该池**最新**流动性低于**已配置**的共享池下限"（默认 1000 USD）。系统只在**退出**时应用这道下限。

于是自然的假设是：**如果入场那一刻该池的流动性就已经低于这同一个已配置下限，那么这笔 −20U 在开仓前就已经注定了**。
这条规则的性质很好——它不是在本账期上搜出来的切点（那是第 26 轮的选择陷阱），
而是系统**自己既有的配置常量**，作用在一个**时点可得**的字段上。

## 2. 实测：假设不成立

2,773 个仓位中 818 个写下线，**每一个都能取到决策快照的流动性**（0 个缺失）。分布：

| 决策时流动性 | 数量 | 占比 |
|---|---|---|
| <1000（低于下限） | **0** | **0.0%** |
| 1000–3000 | 0 | 0.0% |
| 3000–10000 | 77 | 9.4% |
| ≥10000 | **741** | **90.6%** |

**818 个中有 0 个在决策时低于下限。**

按代币看（818 个写下线只来自 **21 个代币**）：每代币决策时最低流动性 min=7,967、p25=20,147、p50=41,167。

**整个入场宇宙的流动性裕度**（2,759 个有决策快照的仓位）：
min=1,840，p01=5,953，p10=10,862，p25=20,443，p50=41,969，p90=199,026。
低于 2× 下限（2,000U）的只有 7 个（0.3%），低于 5× 下限的 19 个（0.7%）。

**结论：观测宇宙从不呈现低于配置下限的决策快照。** 这道下限是一个**入场后事件**，
不是入场前的筛子。**线索关闭**，不做改动。
（也不去搜一个更高的流动性切点——那正是第 26 轮证明会被置换检验杀死的做法。）

## 4. 我在本轮犯的一个 SQL 错误（值得单独记下）

r42 的象限统计里我写了：

```sql
((ds.buys_5m or 0) + (ds.sells_5m or 0))     -- 错
```

**在 SQL 里 `OR` 是逻辑运算符，不是空值合并**：`190 or 0` 求值为 **1**。
于是每一笔的成交笔数都被算成 1 或 2，2,759 个仓位**全部**落进 `trades<30`，
象限表只打出一行。改成 `COALESCE(ds.buys_5m,0)+COALESCE(ds.sells_5m,0)` 后才正确。

> 在 **Python** 里 `or` 返回操作数本身，所以第 41 轮那些探针里同样的写法是**对的**——
> 这也解释了为什么这个错误没有在上一轮暴露。

**新规则 14：在 SQL 里要合并空值必须用 `COALESCE`；`col or 0` 是布尔值。**

## 5. 本轮确立/追加的规则

- **14**：SQL 中 `col or 0` 是布尔值，空值合并必须写 `COALESCE`。（Python 的 `or` 语义不同，迁移表达式时尤其危险。）
