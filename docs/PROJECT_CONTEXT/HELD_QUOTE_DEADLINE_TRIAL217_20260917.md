# Held quote deadline trial and rollback, 2026-09-17

Observed problem: `/api/performance` showed held market-mark loop p95 about 8.66s and actual interval p95 about 9.30s despite a nominal 1s interval. In a rolling 64 Dex held-phase sample, 13 requests failed; held transport p95 was about 5.31s, with host start p95 about 2.42s and HTTP p95 about 3.80s. The complete high-priority batch had a 3.5s `asyncio.wait_for` deadline. Local entry-batch p95 was about .22s, so the measured pressure was external request/queue time, not 214's bounded feature computation. These rolling quantiles cannot be added as if they describe the same request.

An isolated reversible trial changed only that high-priority deadline: first 6.5s, then 5.0s. No API, concurrency, priority, strategy, safety, original-pool floor or account rule changed. The 6.5s worker's later natural short window showed held Dex phase failures 3/39 and market-mark loop p95 ~11.69s, interval p95 ~12.92s. The 5.0s worker showed failures 2/21 and market-mark loop p95 ~11.42s, interval p95 ~16.91s. The baseline 3.5s window had 13/64 failures and loop p95 ~8.66s. Open-held target counts and external/network load changed across these windows, so **none is a matched-load causal comparison**. Fewer observed failures came with materially slower loop tails; neither candidate satisfied both freshness and prompt-exit criteria. `/health` stayed running, Paper only/Live locked, and original-pool gap count was zero in spot checks.

The trial was **rolled back** to the original 3.5s source value and the existing supervisor relaunched the worker at `2026-09-16T19:15:41.687393Z`, PID104364. The loaded runtime hash matches the working source, 507 policies stayed in the same funding period and snapshot frontier reached 984840; no position/account history was reset or modified. The focused existing healthy-held-pool test passed before deployment. There is no committed production code change from this trial. A future manual investigation should compare matched target counts and provider 429/timeout patterns, or redesign held request start pacing independently of the HTTP deadline; increasing a single overall timeout is not currently an accepted optimization. No automatic retry job or periodic review was added.
