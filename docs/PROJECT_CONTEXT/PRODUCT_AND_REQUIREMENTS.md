# 产品与需求基线

## 1. 产品目的

memeTrader 要在普通个人电脑上持续完成两条发现路径：

```text
新闻 / 社交 / 名人账号 / Agent 热点
                ↓
           事件 → 找 Token
                ↘
                  证据汇合 → 主叙事币排名 → 安全门 → Paper 决策与退出
                ↗
    新 Token / 新池 → 反查现实事件
```

目标时效是几十秒到几分钟，不是毫秒级抢跑。真正价值是：每个结论都能回到原始来源、首次本机观察时间、Token 快照、拒绝原因和风控过程。

## 2. 明确非目标

- 不复制一套与 `Runtime / Store / Strategy` 脱节的演示后端。
- 不把旧新闻、身份介绍、推广榜单或未来结果伪装成当时信号。
- 不把 Paper PNL 标成真实利润。
- 不自动登录、滚动、关注、点赞、发帖或规避平台限制。
- 不把密码、Cookie、Session、验证码、私钥或任何 secret 放入项目、Agent prompt、SQLite、Git 或公开 Web API。
- 不为了看起来活跃而生成模拟事件、模拟心跳、模拟 Token 或假成交。
- 不引入 Redis、Kafka、Postgres、Kubernetes 等个人电脑不需要的基础设施。

## 3. 累积用户需求与当前解释

## 4. 事件和来源的推荐信息组织

每个事件先显示聚合结论，再显示证据组：

1. **事件头**：标题、attention、状态、首次/最后观察、独立实体数、决策资格摘要。
2. **来源卡**：平台、发布者/handle、账号类型、原始链接、角色、首次观察/发布时间、freshness、资格。
3. **影响力事实**：已知权威层级、是否官方/已验证、当时可见 follower/reach/互动；不可用字段保持 `unknown`。
4. **时间线**：按本机 `observed_at` 排列，明确后来出现的 confirmation 或 identity。
5. **决策解释**：哪些证据真正参与、哪些仅确认/身份/推广、为什么买或不买。

不要压缩成一个模糊的“影响力分”。至少保留三个正交维度：

- **Authority**：官方一手、主流媒体、专业来源、社区或未知；不是 follower 数。
- **Reach/Heat**：可见关注者、互动量、传播速度；只记录页面当时可观察值和观察时间。
- **Decision eligibility**：时间、角色和本机可用性是否允许它进入当时决策。

展示排序可以综合这些维度，但 API 必须返回排序原因。未知不能自动推断为低质量，也不能自动推断为权威。

跨平台同一实体（例如同一机构的 X、YouTube、Instagram）应使用稳定实体标识去重；否则不能把同一个组织的重复发布算成多个独立来源。该实体级去重仍需在实现和测试中持续核对。

## 5. 社交平台访问现实

| 平台 | 首选采集方式 | 登录现实 |
|---|---|---|
| X | 已登录浏览器中的账号页、搜索页或 Lists | 登录通常有价值；Google 登录可用性取决于页面和地区 |
| Truth Social | 公共/已登录浏览器页 | 可能要求独立账号，不保证支持 Google |
| Bluesky | 公共 Web/API；403 时回退浏览器页 | 公共页优先，注册流程由平台决定 |
| Reddit | 已登录浏览器页；RSS 可能 403/429 | Google OAuth 常见，但仍可能验证 |
| Threads / Instagram | 已登录浏览器页 | 通常依赖 Meta 账号，不应假设 Google 能直接注册 |
| TikTok | 公共/已登录浏览器页 | 可能支持 Google，也可能要求额外验证 |
| YouTube | 公共频道页，或浏览器 Google 会话 | Google 账号天然适用 |
| Telegram | 人工打开 `t.me` 目录链接；自动采集关闭 | Web 登录常需手机号，不自动绕过；页面正文不进入 SQLite/Agent |

浏览器扩展只读取**已经打开并实际渲染的公开内容**。把账号加入 Settings 观察清单并不等于正在采集；还需要对应页面打开、扩展已连接、平台心跳健康。

Gmail 是账号注册的辅助验证通道，不是新闻采集源。即使连接器可用，也只应处理用户当前明确授权的平台验证邮件；不能搜索无关邮件、导出邮箱内容或把验证码保存到项目。

账号研究应优先官方机构目录和官方主页。优先层级建议：官方新闻/机构与项目账号 → 原始公众人物/创作者 → 社区趋势来源。社区和讽刺来源只用于发现，不能作为唯一确认。

## 6. 频率产品原则

用户的最终意图是“比原基线更及时，但不做无意义的极高频”。因此：

- PumpPortal 保持流式；浏览器 DOM 由页面新内容触发并每 30 秒心跳。
- 普通热点 Agent 可从 12 分钟适度缩短，但仍保留 3 分钟 surge、空结果 quiet、fallback/high-token 最短间隔和每日双预算。
- RSS/新池、事件和持仓轮询可在 Settings 白名单内调整；避免因页面刷新频率改变采集频率的误解。
- Web 刷新只读取 SQLite，不会触发 Agent、DEX 查询或新交易判断。
- 精确的设备生效频率只以被忽略的 `config.json` 和 Agent Operations 页面为准，不硬编码在上下文文档中。

## 7. 名人、新闻与热点的客观判断链

名人发布、突发新闻和网络热梗确实能快速聚集 meme-token 注意力，但它们只能说明“可能有叙事窗口”，不能单独证明某个 Token 是正确映射、可以买入或具有持续价格优势。系统必须依次通过五道门：

1. **事件真实且新鲜**：保存原始发布、本机首次观察和发布时间；旧闻、未来结果及事后补充不能回填为当时信号。
2. **来源角色清楚**：区分原始发布、权威确认、社区扩散、身份和推广；名人粉丝量或单条热度不能替代来源角色。
3. **Event→Token 显式关联**：需要 CA、项目官方链接、可复核的命名/内容证据或多条相互独立证据；仅同名、同头像或蹭热点必须保持 `WAIT`。
4. **链上动量确认**：真实新池、流动性、成交量、买卖结构和持续性需要与事件时间窗口一致；社交热度不能替代链上买盘。
5. **安全与 Paper 风控**：可卖性、税、honeypot/rug 风险、canonical margin、仓位和退出规则全部通过后，才允许形成 Paper `CANDIDATE`。

可视化应把这五类信息分栏呈现：名人/来源影响力、新闻权威性、传播热度、Token 映射强度、链上与安全确认。任何一门证据不足，都应明确显示缺口和 `WAIT` 原因，而不是合成一个看似精确的“买入热度分”。

**Telegram 稳定结论：** Telegram 默认只作为经过官网核验的人工发现目录和原始链接入口，不对公共频道做默认自动抓取、索引或 Agent 分析。频道发布者的单方许可不能明显解除 Telegram 平台条款；除非 Telegram/独立法律审查确认具体用途可行，并取得所有相关作者逐一、持续、可撤销且覆盖保存、展示、自动分析和 AI/ML 的同意，否则不直接自动摄取 Telegram 内容。发布者自己在 Telegram 之外提供的 RSS/Atom、JSON、GitHub、状态页等机器 feed 可按其自身条款独立评估。搜索/统计机器人返回值始终是 `discovery-only`，必须回到官网原文或链上证据；条款或权属不明确时保持人工打开或 `paused`，不得影响其他来源运行。详细依据见 `docs/TELEGRAM_SOURCE_RESEARCH_20260830_CN.md`。
