## 0. 一句话结论

1. 我本轮的目标是做一个**因果**检验：第 77 轮说核销队列在"高点"时池子健康、且离核销还有中位
   3.1 分钟。**但"窗口存在"不等于"规则能在窗口里行动"。** 这两件事的差距正是本项目反复栽过的
   前视陷阱（第 36/39/43 轮）。
2. **反事实跑不了，原因在数据。** 我第一版脚本报告"任何回撤档位都不触发"，
   我以为是自己写错了（确实先写错了一次），查出真相是：
   **`chain_meme_trader_market_mark_history` 的序列在核销前是冻结的——76% 的 mark 是重复值。**
3. **一个具体例子**（本轮起点）：

   ```
   仓位 opened 19:13:17，entry_execution_price 3.12312e-05，highest_signal_price 3.672e-05
   17 个 mark，19:20:24 → 19:23:43，**价格全部 = 3.672e-05，流动性全部 = 49999.99**
   整个序列的不同价格值数量：**1**
   核销发生在 19:23:46 —— mark 流里**不存在**任何显示崩塌的观测
   ```

4. **全队列实测（1,019 个可用案例）：**

   | 量 | 实测 |
   |---|---|
   | 整个生期价格**只有一个**不同值 | 82（**8.0%**） |
   | **最后 5 个 mark 价格全同** | **612（60.1%）** |
   | 最后 5 个 mark 流动性全同 | 612（60.1%） |
   | **不同价格数 / mark 数** | p25 0.16 / **p50 0.24** / p75 0.29 |
   | 有任一 mark 流动性跌破下限 | 251（**24.6%**） |
   | **最后一个 mark 仍在下限之上** | **768（75.4%）** |

5. **∴ 对约 75% 的核销仓位，核销所依据的证据从未进入 mark 历史。**
   引擎在**实时**数据上做出了核销决定，而那些数据没有被持久化。

## 1. 这推翻/限定了什么

### 第 77 轮**成立**的部分

> 核销队列不是"从没涨过"的仓位：引擎自己记录的 **85.7% 峰值为正**、中位 +17.1%，
> 而捕获率深度为负（−436.6%）。

**这条与 mark 流的形状无关，成立。**

### 第 77 轮**不能照原样保留**的部分

> "高点时池子健康（966/966），所以确实存在一个可捕获的窗口。"

**问题**：966/966 那个检验问的是"**在记下 running high 的那条 mark 上**，流动性是多少"。
而如果那条 mark 处在一个冻结的序列里，它测量的就是"监控开始时的池子状态"，
**不是**"浮盈时刻的池子状态"。

**能确定的**：记录显示监控开始时池子健康，且**没有任何显示下跌的观测**。
**不能确定的**：市场上是否真的存在过一个"既有浮盈、池子又活着"的时刻。
**∴ 第 77 轮那个"窗口确实存在"的推论，从这份数据里是判不出来的。**

（补充实测：running high **不是**第一个 mark 的比例为 **88.8%**，
所以 high 本身是一个真实的最大值，不是起点。这一点第 77 轮没错。
问题在于序列其余部分是重复值，所以"high 那条 mark"往往就是"最后那条 mark"。）

## 2. 第 78 轮的反事实为什么**跑不了**（而不是"跑出来是 0"）

我原本要测：如果追踪退出**从入场就武装**（而不是像在役各臂那样要求先涨到 +0.20~+0.50），
在这些核销仓位上会怎样。

**答案：这个检验在物理上无法进行。**
一个只读 mark 序列的规则**永远看不到回撤**，因为序列里没有回撤可看——
**中位 76% 的 mark 是重复值，最后 5 个 mark 在 60.1% 的情况下完全不变。**

**所以第 78 轮的"0 触发"不是市场结论，是数据结论。**
我第一版脚本确实有一个真 bug（先更新 running max 再比较，使 `price/peak − 1 ≤ 0` 永远成立），
**但在修好那个 bug 之后，结果依然是 0 触发——因为数据就是平的。**
**两层原因必须分开陈述，否则会把数据缺口误读成"规则没用"。**

## 3. 这对系统能力的直接影响（**准确性 / 可观测性**）

**核销事件在这份数据上是不可审计的。** 具体后果：

1. **无法对核销做历史复盘**：约 75% 的核销没有对应的下跌观测，
   所以"这次核销是否过早/过晚"从留存数据里答不出来。
2. **无法用 mark 流评估任何退出规则**：这是本轮的直接教训——
   我花了一轮才搞清反事实跑不了。**任何基于 mark 序列的退出规则回测都会得到"从不触发"，
   那不是规则的性质，是数据的分辨率。**
3. **`highest_signal_price_usd` 是可靠的**（它是引擎逐帧维护的聚合量），
   所以第 76 轮的捕获率统计**不受影响**；受影响的是**任何需要 mark 时间序列的分析**。

**这不是要求改代码，而是一条必须随结论携带的限制。**
用户 mandate 里的"准确性"（降低误判与漏判）在这一项上的具体体现是：
**不要把 mark 流的"没看到"读成"没发生"。**

## 4. 我本轮自己犯的错（记录）

1. **先写错了一次反事实**：`peak` 在比较**之前**就被当前 mark 更新，
   于是 `price/peak − 1` 恒 ≤ 0，任何回撤档位都返回同一个数、`triggered = 0`。
   **表现形态与第 74/75 轮那次"参数失效"完全同类**：所有参数值给出同一个结果——**这本身就是 bug 的信号**。
2. **发现 bug 后的第一反应是"修好了再跑"**，而修好后数字**没变**。
   我这才去打印真实序列，**看到 17 个相同的价格**。
   **正确顺序本该是先看一条真实数据，再跑全量**——一条样本就能省掉两轮。

## 5. 新增常设规则 31、32

31. **把"数据里没有"与"市场里没有"分开。**
    mark 序列里看不到回撤，既可能是市场没跌，也可能是**观测没记下来**。
    本轮实测：60.1% 的核销仓位最后 5 个 mark 完全不变，75.4% 的最后一个 mark 仍在下限之上
    ——**核销所依据的证据从未进入历史**。
    **在 mark 序列上做任何规则回测之前，先量它的重复率**（本轮：不同价格数/mark 数 p50 = 0.24）。

32. **全量跑之前，先打印一条真实样本。**
    本轮我先跑了 1,019 个案例的全量反事实，两次得到"0 触发"才开始看单条数据——
    而那一条数据（17 个相同价格）立刻解释了全部现象。
    **一条样本的成本是一秒，两轮全量的成本是一小时。**
