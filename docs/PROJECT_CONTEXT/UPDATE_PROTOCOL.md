# 项目上下文更新协议

## 目的

本目录避免重要决策只存在于某个聊天窗口。它不是聊天全文备份，也不是 secret 仓库；只保存能让下一位维护者安全继续工作的稳定事实、需求、决策和验证证据。

## 每次重大任务开始

1. 完整阅读根目录 `AGENTS.md` 和本目录 `START_HERE.md`。
2. 查看当前 `git status`、HEAD、相关代码和测试；不要假设旧快照仍有效。
3. 从私有 `config.json` 只读取完成任务所需的非敏感字段；永远不要把全量配置输出到聊天或文档。
4. 用 `/api/health`、计划任务和 SQLite 只读查询确认设备状态。
5. 识别已有未提交改动及其归属，避免覆盖用户或并行 Agent 工作。

## 什么时候更新本目录

以下任一发生时应更新：

- 产品范围、页面语义或用户需求发生实质变化；
- 安全不变量、交易模式或账号/钱包边界变化；
- 数据 schema、主数据流、部署方式或关键代码路径变化；
- 新的前向误触发、future-data 案例或外部阻塞被发现；
- 发布 SHA、验证结果或设备运行模型变化；
- 重要未完成项完成、取消或被新的明确决定替代。

## 更新方法

- 稳定规则直接更新主题文件。
- 每次发布或重要阶段新建 `SNAPSHOT_YYYY-MM-DD.md`；同日多次可加短后缀。
- 在 `START_HERE.md` 把“最新快照”链接指向新文件，但保留旧快照作为历史。
- 用“已实现 / 正在实现 / 外部阻塞 / 未实现且禁止”四种状态，不使用模糊的“基本完成”。
- 记录测试命令与真实结果；未运行就写“未运行”。
- 记录提交 SHA 只在提交存在后；不要提前写预期 SHA。
- 对外部账号只记录平台、公开 URL/handle、访问方式和状态，不记录个人登录标识或凭据。
- 对公开隧道只记录模式，不记录当前临时 URL 和口令。
- 对钱包只记录网络、脱敏状态和可验证 signature（如有）；不记录私钥或助记词。

## 需求冲突处理

默认情况下，新问题和补充要求只会**追加**到既有目标，不会替换此前计划、研究或构建工作。维护者应在最新快照中保留一份状态明确的累积需求表，并在切换当前工作焦点时继续追踪未完成项。只有用户明确取消，才可移除需求；不能用“最近一条消息”推断旧需求已经失效。

若用户的新要求与当前安全规则冲突：

1. 在需求文件中保留用户目标；
2. 在安全文件中写明当前禁止原因；
3. 在最新快照中标为“未实现且禁止”或“需要独立审查”；
4. 不通过配置漏洞、隐藏按钮或临时脚本绕过。

当前典型例子：用户希望未来能真实交易，但 `AGENTS.md` 要求 `live.enabled=false`。因此保存目标，但只实现 Paper 自动策略和隔离 Devnet 人工验证，直到有新的独立 Live 设计审查。

## Secret 清单

更新前后都要搜索并删除意外出现的：

- 私钥、助记词、密码、验证码、Cookie、Session；
- Bridge Token、API key、通知 token、Chat ID；
- 公开入口口令或包含口令的 URL；
- `config.json` 全量内容、SQLite 数据和浏览器材料。

用户在聊天中提供 secret 不等于允许把它写入项目。应指导用户使用 loopback UI 或本机密码管理器；已粘贴过的私钥应视为暴露。

## 完成一次上下文更新的检查表

- [ ] `AGENTS.md` 仍是最高级规则；
- [ ] `START_HERE.md` 指向最新快照；
- [ ] 已实现和未完成没有混写；
- [ ] 没有虚构运行状态、测试、登录或交易；
- [ ] 没有 secret、私有 DB 数据或临时公开凭据；
- [ ] 新增文档链接可从 `README_CN.md` 和 `START_HERE.md` 找到；
- [ ] `git diff --check` 通过；
- [ ] 与并行代码改动无冲突。
