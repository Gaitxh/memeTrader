## 0. 一句话结论

1. **没有故障。** 我一度判定"整个流水线冻结 8 小时"，那是**我自己的读法错误**：数据库把时钟写成
   带 `Z` 的 UTC，而我是拿它去和**本地时区（UTC+8）的文件 mtime** 比。健康系统被我读成了停摆。
2. **金狗实验（`exit_ladder150`）没有卡死**，它只有 **29.6 分钟大**，不是第 67 轮我推算的 8.4 小时。
   12 个 cohort 是在 **165 秒的一次入场爆发**里开的，此后 8 个槽位一直占满，所以没有新 cohort。
3. **0 个分歧不是缺陷，是概率事件**，但**峰值贴在上限上**：12 个 cohort 里跑得最好的那个 running max
   = **1.1027**，而首个止盈档就在 **1.10**。差千分之三。
4. 由此得到本轮真正有用的东西：**六个配对的可读性排序**（需要多少 cohort 才能凑够 20 个分歧），
   以及**这个实验对 42% 的 cohort 在结构上不可能产出信息**这一设计事实。

## 1. 纠错一：我把一个健康的系统读成了停摆

### 我做了什么

排查第 67 轮遗留的 P0 读数时，我先看 `chain_meme_trader_positions.last_evaluated_at`，得到
`2026-09-13T00:09:22`，而当时本地时间 `08:08:49`；`chain_meme_trader_marks`、
`token_snapshots`、`token_discovery_exposures` 等**每一张表**的最大时钟都停在 `00:10` 附近；
`/api/live` 返回的 `generated_at` 也是 `00:10:48`。

我据此写下结论：**"运行了 8 小时的空转"**，并准备重启服务。

### 实际是什么

```
local now      : 2026-09-13T08:12:38+08:00
utc now        : 2026-09-13T00:12:38Z
py utc now     : 2026-09-13T00:12:38+00:00

db  row   max(last_evaluated_at) = 2026-09-13T00:12:54.118760Z
file mtime (local)               = 2026-09-13T08:12:56
```

**数据库里的时间戳是准确的 UTC。** 我拿来对照的是**本地时区**的文件 mtime，两者差 8 小时。
`00:12Z` 就是 `08:12+08:00`——数据是**当场写的**。

### 用一次 before/after 观测把它钉死

同一个只读连接、间隔 40 秒读两次（`r68h_watch.py`）：

| 表 | T0 | T1（40 秒后） |
|---|---|---|
| `chain_meme_trader_positions` | 3,882 行 / `00:11:14` | **3,885 行 / `00:12:00`** |
| `chain_meme_trader_v6_entry_evaluations` | 77,427 / `00:11:50` | **77,627 / `00:12:31`** |
| `token_snapshots` | 77,430 / `00:11:51` | **77,640 / `00:12:32`** |
| `provider_post_ambiguity_admissions` | 214,723 / `00:11:50` | **215,433 / `00:12:32`** |
| `token_discovery_exposures` | 116,720 / `00:11:51` | **117,109 / `00:12:32`** |

文件大小 `2,484,748,288 → 2,487,861,248`（+3.1 MB / 40 秒）。

以及 `/api/live` 的实时值：`heartbeat_age_seconds = 0.047`，`open_position_count = 302`。

**运行时时时在写、心跳亚秒级、302 个在仓。没有任何故障。**

### 我差点造成的伤害

我当时正要"重启服务"。对一个**健康**的生产进程做重启，会：中断 302 个在仓的逐仓估值循环、
让一次入场爆发中的头部 cohort 丢失观测租约、并把一个 29.6 分钟大的实验的前沿打乱。
**这是本轮最严重的风险，且它完全来自我的读法。**

### 这条要成为规则

> **规则 47**：在这个库里比对"数据是否新鲜"之前，先把**同一时刻**用两种时钟写出来验证：
> 数据库的时钟列是**带 `Z` 的 UTC**，而文件 mtime、`Get-Date`、任务计划日志
> （`paper-supervisor.log` 用的是 `+08:00`）是**本地时间**。本机两者差 **8 小时**。
> 判定停摆前必须至少做一次 **before/after 双读**（同一连接、间隔数十秒、看**行数**而不只是
> 最大时间戳）——因为"最大时间戳不变"也可能是窗口内本来就没有新事件。

顺带纠正一个我先前的错误假设：我一度以为时钟列是**无时区的裸 UTC**。实测 **171 个时钟列全部带
尾随 `Z`**，这个假设是错的（`r68i_clock_and_artifact.py` 第一节）。

## 2. 纠错二：金狗实验的真实年龄是 29.6 分钟，不是 8.4 小时

同一个时钟错误污染了我对实验的判读。第 67 轮我按"前沿 `2026-09-12T23:42:11` → 现在"算出
8.4 小时，并据此说"结算率只有 0.48 cohort/h"。

实测（`r68j_wait_time.py`）：

```
ladder first cohort 2026-09-12T23:42:56.016215Z
ladder last  cohort 2026-09-12T23:45:40
fleet now           2026-09-13T00:12:32

the 12 cohorts opened inside 165 s, 29.6 min ago (one entry burst, then the cap is full)
cohorts opened 12   settled 4   still open 8
```

- 12 个 cohort 全部落在 **165 秒**的窗口里 = **一次入场爆发**，之后 8 个槽位占满，没有新 cohort。
- 实验只有 **29.6 分钟**大。吞吐 = 12 / 0.493 h ≈ **24.3 cohort/h**（不是 0.48）。
- 四个臂的前沿**完全相同**（`23:42:56`），四个臂**逐 cohort 锁步**：12 个 cohort 全部被四个臂
  同时持有，**0 个 mixed-status**。这是载体臂按设计的正确形态。

舰队级的入场确实是**爆发式**的（`r68j` 第 4 节）：191 个有入场的分钟里，每分钟中位数 7 个、
p90 56 个、最高 **128** 个；而单臂整点计数是 22、19、11、7……**入场按爆发到达，不是均匀流**。
这解释了为什么槽位会在几分钟内从 0 打到满，然后一段静默。

## 3. 金狗实验的分歧功率：实测，不是假设

### 3.1 先把上一轮的假设换成实测

第 58 轮设计这个实验时估"约 3.4 个分歧/小时"，那是**对"多少 cohort 能涨到 +10%"的假设**，
从未实测。现在实测（舰队 rolling max 的 CDF，n = 全部有 running max 的仓位）：

| 门槛 | P(running max ≥ 门槛) |
|---|---|
| +5% | 0.6894 |
| **+10%** | **0.5795** |
| +15% | 0.4591 |
| +20% | 0.3798 |
| **+25%** | **0.3286** |
| +30% | 0.2710 |
| +100% | 0.0486 |

（注：本轮先后跑出 0.5702 与 0.5795 两个值——前者是 n=3,776 的样本，后者是 n=3,886 的更大样本，
随新仓位写入而增长。引用时用后者并注明 n。）

### 3.2 由此得到六个配对的可读性排序（这是本轮净新增的结论）

**只有当 cohort 的 running max 落在两个档位之间时，这两个臂才会分歧。** 所以每个配对有一个
"分歧带宽"，带宽越窄越难读：

| 配对 | 分歧带 | P(带) | 凑够 20 个分歧需要 |
|---|---|---|---|
| `t10` vs `t25` | [0.10, 0.25) | 0.2509 | **80** cohort |
| `t10` vs `t20` | [0.10, 0.20) | 0.1997 | 100 |
| `t15` vs `t25` | [0.15, 0.25) | 0.1305 | 153 |
| `t10` vs `t15` | [0.10, 0.15) | 0.1204 | 166 |
| `t15` vs `t20` | [0.15, 0.20) | 0.0793 | 252 |
| `t20` vs `t25` | [0.20, 0.25) | 0.0512 | **391** |

**可执行结论：读数顺序应按带宽从宽到窄。** `t10 vs t25` 最先可读（80 个 cohort），
`t20 vs t25` 最后（391 个）。不去逐个等最窄的一对。

### 3.3 0/12 是什么性质的事件

按 P(带)=0.2509 算，12 个 cohort 期望分歧 **3.0** 个；出现 **0** 个的概率约
`0.7491^12 ≈ 3.1%`。**偏背运，但不是不可能**，样本只有 12。

**但真正值得注意的是峰值贴边**：四个臂的 12 个 cohort 里 running max 的最大值是 **1.1027**，
而首档就在 **1.10**。也就是说——**这个实验的第一个分歧，此刻只差千分之三**。
`r68c` 里 settled 的 4 个 cohort 也印证了机制：它们的退出原因是
`market_mark_hard_stop`（×3）与 `dex_pool_liquidity_below_configured_floor`（×1）——
**这两条退出路径在四个臂里是完全相同的**，所以它们必然 0 分歧。

### 3.4 由此暴露的一个设计事实（本轮第二个净新增结论）

载体臂之间**唯一**的差别是首档位置，而 `hard_stop_return=-0.35`、`trailing_activate_return=0.30`、
`trailing_drawdown=0.35`、`max_hold_minutes=90` 在四个臂里**完全相同**（第 68b 轮逐字段读过有效定义）。
于是：

> **一个 cohort 只有在先涨到 +10%（最低那一档）之后回落，才可能让四个臂产生分歧。**
> 从未涨到 +10% 的 cohort —— 按实测 **42.05%**（`1 − 0.5795`）—— 在四个臂里走**完全相同**的
> 硬止损 / 最长持有 / 追踪退出路径，**对这个实验的结构零信息**。

这不是缺陷（同前沿单因子设计本来就该如此），但它决定了实验的信息产出率**只**由
"涨到 +10% 的比例"和"涨到之后怎么走"决定，而**不能**靠加长观察时间或增加槽位把那 42% 变成信息。
它也是"为什么 12 个 cohort 只出 0 个分歧"的**完整机制解释**，比"样本小"更有解释力。
