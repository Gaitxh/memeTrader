# 第 75 轮记录：窗口长度扫描——被 gate 检查的 30 秒**不是**最优值，60 秒合格帧数多 21%

> ## ⚠️ 第 76 轮更正：本轮的**结论方向是错的**，请先读 `ROUND120_76_RECORD.md`
>
> 本轮以**合格帧数**为目标，得出"60 秒比 30 秒多 21%，30 秒坐在峰的偏低一侧"。
> **第 76 轮证明这是错的优化目标。**
>
> - 那 +21% 的帧**全部落在本来就已经有 ≥3 帧的 2,501 个序列里**（1–2 帧的 15,802 个序列
>   在**任何**窗口长度下都是 0 合格——三帧下限与窗口无关）。
> - 换成**正确的目标（能触达多少不同 token）**后，**60 秒反而更少**：
>   **30 秒触达 230 个 token，60 秒触达 221 个**（−9）。
>
> 机制：`window(rows, seconds)` 需要**不晚于 `t_end − seconds`** 的帧，
> 所以整个生命期短于 60 秒的序列**永远**无法形成 60 秒窗口。
> 实测 **66.0% 的序列生命期 < 60 秒**，其中 30 秒能触达 2 个、60 秒触达 0 个。
>
> **因为 gate 是逐 token-帧评估的，一个合格帧就能让该 token 在该帧不被拦——
> "触达"才是正确目标，"帧数"不是。**
>
> **∴ 本轮的"60 秒更好"结论撤回。窗口长度不是一个可用杠杆**（§10.19 已同步更正）。
> 本轮的**测量工具与测试仍然有效**（`scripts/window_size_sweep.py` 及其 10 个测试），
> 只是**优化目标必须换成触达数**——第 76 轮已把这个更正做成 `--objective reach` 与回归测试。

## 1. 复刻的合约（逐行对应）

```python
# dex_trajectory.py:49-55
def window(rows, seconds):
    end = rows[-1]['t']
    eligible = [i for i,r in enumerate(rows) if r['t'] <= end-seconds]
    if not eligible: return None                                   # (A) 需要满额回看
    part = rows[eligible[-1]:]                                     # 从"最后一个不晚于截止的行"起
    if end-part[0]['t'] > seconds+max(5,seconds/3): return None     # (B) 跨度上限 = seconds+max(5,秒/3)
    if any(b['t']-a['t']>30 for a,b in zip(part,part[1:])): return None  # (C) 相邻间隔 ≤30 秒
    if len(part)<3: return None                                    # (D) 至少 3 帧
```

**第 74 轮我错在哪**：我在套用规则**之前**把序列切成恰好 3 帧，
于是 `part` 永远是 3 个点，**窗口长度变得无关**，60/120/300 秒返回同一个数（27,753）。
**正确做法是让 `part` 从截止行一直延伸到末尾**——一个 300 秒窗口因此可以容纳很多帧。

## 2. 哪条规则在卡（同一次扫描）

| 窗口 | (A) 无满额回看 | (B) 跨度超限 | (C) 间隔 >30 秒 | (D) 少于 3 帧 |
|---|---|---|---|---|
| 5 秒 | 26.0% | **52.6%** | 0.0% | 4.1% |
| 15 秒 | 26.3% | **46.1%** | 0.0% | 8.1% |
| **30 秒** | 26.8% | **38.1%** | 5.7% | 0.0% |
| **60 秒** | 27.5% | 25.6% | **11.2%** | 0.0% |
| 180 秒 | **35.1%** | 14.5% | **20.3%** | 0.0% |
| 300 秒 | **40.4%** | 11.8% | **22.0%** | 0.0% |

**读法**：窗口太小时，**跨度上限**是主因（5 秒档 52.6%）；
窗口太大时，**满额回看**（300 秒档 40.4%）和**间隔断裂**（22.0%）接管。
**30 秒正好处在"跨度上限仍然很大（38.1%）、而间隔断裂还没起来（5.7%）"的位置——
也就是说 30 秒把大量本可合格的帧挡在了跨度上限上。**

## 5. 为什么本轮**不建议直接改**（边界声明）

**用户的原则是硬约束**："允许设计更复杂、覆盖更多场景的策略，但必须以**额外策略模块**形式加入，
**严禁修改或替换任何现有策略**。" 改 `store.py:27784` 读哪一档，会**直接改变 330 个策略里
所有 `requires_distinct_trajectory_frame=True` 的臂的入场行为**——那是修改现有策略，**不允许**。

**除了授权问题，技术上还有三条没有回答：**

1. **合格 ≠ 可交易。** 本轮只证明"窗口能形成"，**没有**证明形成后会有策略受理。
2. **更长的窗口测量的是更慢的现象。** 窗口的输出同时喂给 velocity、acceleration、
   realized_volatility（`dex_trajectory.py:56-69`），窗口一变，**这些信号的含义就变了**。
   21% 更多的合格帧**不等于** 21% 更多的正确信号。
3. **没有回答盈利性。** 窗口更长是否更赚钱，本轮**完全没有**回答，也不该从合格率推断。

**正确的落地形式（供用户决定）**：新增一个**额外策略模块**，
其中 `requires_distinct_trajectory_frame` 的臂改用一个 60 秒档位的 gate，
与现行 30 秒档位的臂**并行**前向运行，各自积累证据——这样既遵守"只增不改"，
又能用同一口径比较两个档位。**本轮只交付测量工具与结论，不部署。**
