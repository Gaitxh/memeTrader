# 第 86 轮记录：30 个候选槽位的上限是**自己设的**，不是数据源逼出来的；但"报价触达"不等于"观测触达"

日期：2026-09-13
前置：`ROUND120_85_RECORD.md`
本轮性质：**把用户唯一剩下的那个决策项（观测槽位预算）从"该不该动"拆成"动了会不会有用"，
并给出两侧的实测。** 没有改任何策略、阈值或运行时行为。

## 0. 一句话结论

1. 第 85 轮把 P0 收敛到一条：**唯一诚实的优先事项是提高 N**，而放大器是观测槽位预算
   （第 65/73 轮闭环）。那是**用户决策项**。本轮只回答一个问题：
   **这 30 个候选槽位的上限，是我们自己设的，还是数据源逼出来的？**

2. **实测：是自己设的。** 两条独立证据：

   | 证据 | 实测 |
   |---|---|
   | 候选桶占用（运行时内存计数器直读） | **8 / 9 桶已满** |
   | 48 个数据源里记录在案的限流/429 错误 | **0 条** |
   | 最近一次成功抓取的年龄 | **约 0 秒**（参考时刻与最新成功同一秒） |

   `non_held_by_chain_bucket` = `{bsc:{early:3,growth:4,mature:3}, robinhood:{3,2,3},
   solana:{3,4,3}}`，`base_caps` = `{early:3, growth:4, mature:3}`，
   **且持仓不占这些槽位**（`runtime.py:7894` 只判 `if key not in held`）。
   所以 FULL 的含义是**候选在队列里等**。

   收尾复测（本轮结束时）：**9 / 9 桶全部满**（robinhood growth 也填满了），
   同时运行时健康：最新 mark 0.8 秒、最新 snapshot 2.4 秒、最新入场判定 10.6 秒
   （全部用**库内 UTC** 对比库内 UTC，规则 47）。**满仓是稳态，不是瞬时**。

3. **但本轮更重要的产出是一个否证，它挡住了我本来会写下的标题。**
   报价路径**已经**触达到远超 30 个的代币：

   - 15 分钟内**有 280 个从未持仓的代币拿到了新报价**（marks），每个中位 **14 次**
   - 按 30 个候选槽位算，这是 **9.3 倍**

   我第一版据此写的标题是"报价路径已经覆盖 9 倍于上限的代币，上限是唯一在丢弃这些工作的东西"。
   **实测把这个推论打断了：**

   | 同一批 280 个代币 | 实测 |
   |---|---|
   | 窗口内 **0 条** snapshot 的比例 | **81.3%** |
   | 窗口内 **≥3 帧**（闸门要求）的比例 | **2.8%** |
   | **有史以来**累计 snapshot 数的中位 | **1** |

   **∴ 一次报价不是一帧。** 报价路径的触达**不能**证明观测路径的触达。
   **稀缺的仍然是"驻留"（lease）产生的帧，不是报价。**
   这条限制同时**加强**了上面的结论（上限是自己设的，可以调）和**限制了**它的价值
   （调高上限买到的帧，按第 65 轮边际产出 ≈4.7 个密集窗口/槽位/小时计价，
   而不是按 280 个代币计价）。

4. **对用户目标的直接含义**：这是一个**真的可以做的决策**（不是被外部约束锁死的），
   但它的收益单位是**帧/小时**，不是"280 个代币"。而且第 85 轮已测出
   **94 个代币里只有 6 个盈利**——**更多代币是更多证据，不是更多钱**。
   **本 session 不触碰该设置。**

## 1. 我自己本轮错了三次，三条都保留可见（规则 35 的应用）

### 错误 1：把被截断的面板当成总体

第一版我打印了 **"live leases: 9"**，当成"调度器现在持有 9 个租约"。实际是：

```
observation_leases145.dump_state(watch, now, *, limit: int = 30)   -> 至多 30 行
observation_leases145.bounded_summary(watch, now, *, limit: int = 30) -> 同一个默认值
```

**面板行数是下界，不是总体。** 本轮实测该面板此刻持久化了 16 行——既不是 9 也不是 30，
所以**连"截断得紧不紧"都无法从面板本身判断**。
已修：`scripts/lease_panel_readout.py` 现在把这条警告打在输出里、写进模块 docstring，
并且把 JSON 字段从 `live_leases` 改成
`lease_rows_persisted` + `count_is_lower_bound: true` + `panel_truncation_limit: 30`
（机器可读形式里也不能留下能被误读成总体的字段名）。新增 3 个测试，共 9 个通过。

### 错误 2：用混合流量的速率冒充请求速率（**已撤回**）

我拿 `chain_meme_trader_market_mark_history` 的**总行数**除以 epoch 跨度，
再和 HTTP 客户端 0.6 秒/主机的节流下限比，得出"请求余量"。
**那张表是混合流**：持仓标记、候选报价、窗口内已平仓的标记都写在里面，
而且一次请求可以写多行。**它不是任何单一流的请求速率。**
已撤回，不进结论。

### 错误 3：`>` 用在 set 上不是比大小

我把 280 个"从未持仓"和 17 个"窗口内持仓过"的代币分成两个 `set`，然后写：

```python
if never > held_in_window:      # 我以为是 280 > 17
```

**Python 的集合 `>` 是超集判断，不是比大小。** 两个不相交的集合恒为 False，
于是 **280 vs 17 走进了 "READING: MIXED / 大部分是持仓在churn" 的分支**——
和它上一行刚打印出来的计数**直接矛盾**。修法是 `len()` 两侧都加，
并且**让分支把它据以判断的计数打印出来**（`branch driver: never=280 held_in_window=17`）。
**一个还会自信地措辞的错误分支，是错误结论进入报告的通道。**

### 错误 4：把累计计数器当成每轮计数

我把 `runtime_timing_latest.components.flat_target_selection.items = 13,225` 按
`sample_count = 120` 相除，得出"每轮约 110 个目标"。
读代码后确认：`runtime_timing.py:120` 是 `timing["items"] += int(items)`（**累计**），
而 `sample_count` 是 `deque(maxlen=MAX_SAMPLES)` 的**有界队列长度**。
**两者不可相除。** 该推论已从本文删除，改用车道自己表里的行数与时间跨度。

## 2. 归因：那 280 个报价是谁取的？

**不靠猜。** 先读调用图（规则 51：先证明一条路径跑过）：

| 车道 | 目标集 | 本轮实测 |
|---|---|---|
| 主车道 `runtime.py:7697` | `chain_meme_trader_market_mark_targets()` = 持仓 + 待执行 | **12 个目标**（`actual_open 12`） |
| flat 阴影车道 `runtime.py:7724` | `FlatSelector.due_targets(limit=30)`，**非持仓** | 窗口内 **34 个**代币 |
| `complementary_market_data_once` / `_poll_gecko_network` | 广域互补行情 | 组件节拍 **10.0 秒**（p50 10.03，73 个样本） |

- flat 阴影车道的 34 个**全部**落在那 280 个之内，所以它是来源之一，
  但**最多解释 34 / 280**。
- 剩下的是互补行情车道：它每 10 秒跑一次，在轮转的非持仓宇宙上写 marks。
  这与"每个代币中位 14 次报价 / 15 分钟"（≈每 64 秒一次）的节拍一致。
- flat 阴影车道自己的表 `chain_meme_trader_flat_breakout_shadow` 累计 **1,960 行**
  （2026-09-12T18:27:12Z 起，最新行 12 秒前），即约 **267 条/小时**的非持仓观测——
  同样是 30 个候选槽位的数倍。
  （注：`runtime_timing.components.*.items` 是 `timing["items"] += int(items)`
  的**累计值**（`runtime_timing.py:120`），而 `sample_count` 是 `maxlen` 有界队列长度，
  两者**不可相除**求每轮目标数。我第一版曾按 120 个样本去除，已改掉。）

**结论：报价不是瓶颈。** 系统已经在为几百个非持仓代币反复取价，
而这些价格**以 marks 形式存储、不构成帧**。

## 3. 与整条断崖链的关系（更新后的唯一解释）

```
实际交易量偏低
  ↑  全 epoch 只有 690 个 cohort 产生了仓位；4,643 个仓位只是 94 个代币的复制品（第 84 轮）
  ↑  入场闸门 await_distinct_dex_trajectory_frame 占 46.41% 的逐臂判定（第 72 轮）
  ↑  放行要求 ≥3 帧 / 跨度 ≤40 秒 / 相邻间隔 ≤30 秒（第 73 轮）
  ↑  86.4% 的 token 只拿到 ≤2 帧、63.7% 只有 1 帧（第 71/73 轮）
  ↑  帧只来自观测驻留（lease）；候选槽位上限 30
  ↑  而这 30 是【自己设的】：8/9 桶满 + 0 条限流记录 + 最新成功年龄 ≈0 秒（第 86 轮）
  ↑  同时报价路径已经触达 280 个非持仓代币/15 分钟、每个中位 14 次（第 86 轮）
     ——但其中 81.3% 窗口内 0 帧、中位累计 snapshot 只有 1 条
  ∴  瓶颈精确定位为【观测驻留的额度】，而不是【数据可得性】、【节流】、【发现能力】
      或【策略过滤】。额度是自己设的 ⇒ 这是一个真实可做的用户决策。
```

**必须同时说清的边界**：额度可以调，**不等于**调了赚钱。第 85 轮：94 个代币里 6 个盈利
（6.4%，90% CI [3.3%, 11.9%]）。**把 N 从 94 提到 157 是把一个不稳的比例变得可读，
不是把它变成正数。** 这正是第 85 轮"P0 = 提高 N"与"P1 = 保持第 82 轮假设在前向队列"的关系。

## 5. 新增常设规则（接 §10.6 同族）

40. **区分"自己设的上限"与"外部给的上限"，并读运行时关于自己的状态。**
    候选槽位 8/9 桶满、48 个源 0 条限流记录、最新成功年龄 ≈0 秒 ⇒ **上限是自己设的**。
    判据必须来自 `non_held_by_chain_bucket` 这种**内存计数器的直读**，
    不能用"被截断的面板"（下界）或"混合流量的速率"（第 1 节错误 2）代替。

41. **一个 checkpointer 写下来的列表默认是下界。**
    `dump_state(..., limit: int = 30)` / `bounded_summary(..., limit: int = 30)`：
    面板行数 ≤30，**行数不是总体**，而且"截断得紧不紧"也无法从面板本身判断。
    我本轮先把它读成了总体（"live leases: 9"）。

42. **`>` 用在 set 上不是比大小，是判断超集。**
    `never > held_in_window` 对两个不相交集合恒为 False，于是 280 vs 17 走了
    "MIXED / 大部分是持仓在 churn"的分支——与上一行刚打印的计数直接矛盾。
    **让每个分支把它据以判断的计数打印出来**；否则错误分支会带着自信措辞进报告。

43. **一次报价（mark）不是一帧（frame）。**
    引擎已为 280 个非持仓代币每 15 分钟各取约 14 次新报价，
    但它们**中位只有 1 条 snapshot、81.3% 在窗口内 0 条、只有 2.8% 达到 ≥3 帧**。
    **报价路径的触达不能证明观测路径的触达**——这正是我第一版"9.4× 上限"标题必须
    被自己打断的地方。
