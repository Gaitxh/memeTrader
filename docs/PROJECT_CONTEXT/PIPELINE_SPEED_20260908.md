# 数据获取与分析路径提速（2026-09-08）

用户本轮授权进一步优化发现、获取、计算、分析和判断速度。实施范围为当前链上Paper运行路径，不增加策略、不改变账户资金期，不放宽原池身份或时序规则。

## 已确认并修改的三处问题

1. **跨链补全串行等待。** 同一批待补全币按链分组后，原代码等待前一条链全部返回、处理，才请求下一条链。现在每条链独立协程，请求返回后立即入库并唤醒判断。单链内部仍按最多30地址一批；当前每5秒最多10个待补全目标、既有180/90秒配置上限和共享限频保持。没有为并行多取队列目标。测试阻塞BSC请求后，Solana报价仍完成持久化并发出判断唤醒。

2. **低优先请求可占满持仓并发容量。** 原先8个共享槽无优先级预留，低优先请求一旦开始，后来的持仓请求只能等待。现在总并发仍为8，低优先最多5，保留3个槽供三条持仓链请求。原池exact补充请求也受同一限制；无容量时直接交给后续独立补源，不排队拖住Gecko/Demo。429与传输错误仍遵守原共享退避；没有把限流失败当空报价。取消和异常会释放槽，退避等待不占全局槽。

3. **共享分析重复深复制。** `consume_passive_cohort_batch` 已深复制整个状态，随后又深复制历史、克隆episode、resilience episode和单币历史。删除后四处重复，保留入口的一次完整隔离。旧状态仍不受后续帧或返回对象修改影响。

## 验证

- 23个不同定向用例通过，覆盖低优先饱和时三链持仓进入、取消后释放容量、共享退避、原池先返回即应用、独立补源不中断、跨链补全先完成先持久化、每轮额度、旧状态隔离和原有cohort信号规则。初次原池测试的最小构造对象缺少原本由Runtime初始化的并发字段，补齐测试fixture后通过。
- 对一份真实保存的200币状态及其最后30帧做相同输入复放，各20次：函数平均 **6.545ms → 3.263ms**，约减少50%。输出逐字一致，输入状态未改变。此结果只代表该函数的本地复放，不代表端到端延迟降低50%。
- 证据位于 `data/research/pipeline_speed_20260908/`：`before.json`、`pre_deploy.json`、`cohort_profile_input.json`、`cohort_before_output.json`、`cohort_optimization.json`、`after_initial.json`、`after.json`。

## 没有采用的改法

新来源链接已写入来源记录。没有证据证明每个已hydrated币收到新推广链接后都缺行情，故不把它们全部重新排队挤占新币额度。当前链上模式的hydration分支也不会进行所怀疑的BSC旧安全查询，没有为速度关闭GoPlus/Honeypot安全检查。已存在的发现链过滤、原生事件尾部处理、新来源唤醒no_pair、5秒小批补全和行情唤醒保持。

本轮改善同等请求额度下的等待与计算效率，不宣称已增加独立发现数量；实际新增覆盖仍需看上游收录、数据质量和自然运行结果。未发现安全、低成本且有明确当前证据支持的新数据源扩展，不为提高发现计数重复采集相同信息。
