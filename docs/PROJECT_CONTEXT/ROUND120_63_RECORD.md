# ROUND 120-63 — 用**生效定义**复核第 57 轮的契约差异：前提成立，我交付的模块站得住

日期：2026-09-13

## 1. 为什么必须复核

第 62 轮发现我在两轮内**三次**把"注册的策略"当成"生效的策略"。而第 57b 轮的结论——
`full15` 与 `full25` **不只差止盈档位，追踪激活也不同（0.30 vs 0.35）**——
**正是读注册 JSON 得出的**。而那个结论是 `exit_ladder150` 模块存在的**全部理由**
（四个臂把追踪激活钉死在 0.30，好让只有档位在变）。

**如果生效定义把追踪激活也归一化了，那么这条对子本来就是单因子，
我交付的模块就建立在一个"草稿值"的假象上。**

所以必须复核，`expected` 不算数——**"预期如此"正是上一轮产生三个错误结论的推理方式。**

## 2. 复核结果：前提成立

**`exit150_full15_v1` vs `exit150_full25_v1`，生效值逐字段：**

| 字段 | full15 | full25 | |
|---|---|---|---|
| `take_profit` | `[{return: 0.15, frac: 1.0}]` | `[{return: 0.25, frac: 1.0}]` | **不同** |
| **`trailing_activate_return`** | **0.3** | **0.35** | **不同** |
| `trailing_drawdown` | 0.35 | 0.35 | 同 |
| `hard_stop_return` | −0.35 | −0.35 | 同 |
| `max_hold_minutes` | 90 | 90 | 同 |
| `notional_usd` | 20.0 | 20.0 | 同（已归一化） |
| effective cap | 8 | 8 | 同（已归一化） |
| `trajectory_exit` | None | None | 同 |
| `entry_match_mode` | `isolated_cohort_observer` | 同 | 同 |

**去除身份键后的行为差异字段：`['take_profit', 'trailing_activate_return']`。**

> **结论：第 57b 轮成立，混淆在生效契约里是真实的，`exit_ladder150` 的立论基础成立。**

## 3. 我交付的四个臂：**生效契约下确认为单因子**

| 检查 | 生效值 |
|---|---|
| 行为差异字段 | **`['take_profit']`** —— 只有它 |
| `trailing_activate_return` | **{0.3}（四臂一致，已钉死）** |
| `notional_usd` | **{20.0}（四臂一致）** |
| 生效并发上限 | **{8}（四臂一致）** |
| 四个档位 | 0.10 / 0.15 / 0.20 / 0.25 |

**即：第 58 轮部署的模块，在生效定义里确实只有首档位置在变。**
（第 58b 轮是从注册 JSON 验证的；本轮从生效定义验证——**两个来源都通过**。）

## 4. 顺带确认：混淆是"+25% 变体"的系统性特征

| 对子 | 生效行为差异字段 | 判定 |
|---|---|---|
| `full15` vs `full25` | `take_profit`, **`trailing_activate_return`** | 非单因子（档位 + 追踪） |
| `bank15` vs `bank25` | `take_profit`, **`trailing_activate_return`** | 同样非单因子 |
| `t30` vs `v5k` | **无** | **单因子** ✓ |
| `r15` vs `r15a30` | **无** | **单因子** ✓ |

**所以"两个 +25% 臂都把追踪激活抬到 0.35"是一个系统性的设计选择，不是笔误**——
它意味着**舰队里两个档位对比（full 与 bank）都无法干净归因于档位**，这正是新模块存在的理由。

两个下限对子是单因子（差异在 `entry_filter` 里的下限声明，**那就是处理本身**）。

## 5. 我的检查器又被"身份键"绊了一次（第 3 次）

首次运行时，四个梯子臂被报成 `NOT single-factor`，差异字段是
`['entry_filter', 'runtime_addition_id', 'take_profit']`。
**`runtime_addition_id` 是注册身份，不是行为**——我的身份键集合里漏了它。
补进身份键后即得 `['take_profit']`。

**这与第 58b 轮漏掉 `direction` 是同一个错误，且我用同一句注释写进了修好的代码里。**

> **规则 32 需要加强**：单因子检查器的身份键集合**必须逐次枚举**，
> 而不是"想到哪个加哪个"——本 session 已因漏 `direction`、漏 `runtime_addition_id` 各错一次。

**另注一处措辞不精确**：探针 E 段对两个下限对子打印
`identical after stripping direction: False`，那**不是缺陷**——
它们的 `entry_filter` 差异**就是下限声明（处理）**，所以剥掉 `direction` 后当然不同。
该行的标签沿用了只适用于退出对子的假设，**据实记录**。

## 6. 追加规则

- **39**：**验证一个"前提"要与验证它时用的来源同级，或更高。**
  第 57b 轮读注册 JSON 得出结论、第 58 轮又用注册 JSON 验证自己——
  **两次同一来源，等于没验证。** 第 62 轮暴露来源问题后，本轮改用**生效定义**复核，
  才是真正的独立确认。（这也解释了为什么第 58b 轮"通过"并不能让我安心。）
- **32（加强）**：单因子检查器的身份键集合必须**逐次完整枚举**；
  漏一个身份键就会在正确代码上报错。已发生两次（`direction`、`runtime_addition_id`）。
